# RSVP, персональное приглашение и polish

Дата: 31.10.2026. Все изменения локальные. Production, Amvera, production PostgreSQL, Telegram webhook и deployment не запускались. Push/commit не выполнялись. Существующие незакоммиченные правки проекта сохранены.

## 1. Подтверждение RSVP

Заголовок: «Спасибо, мы всё сохранили!». Под ним «Ваши ответы» и все фактически сохранённые имена текущей guest session со статусом «Приду» / «Не приду». Ответ API, а не незавершённая форма, является источником списка.

Главное действие «Скачать приглашение» скачивает один PDF. Повторное скачивание доступно после reload. Ошибка генерации/скачивания отображается отдельно, не удаляет ответы и не выдаёт ошибку за успешное скачивание.

Второе действие «Добавить ещё гостя» очищает поля и переводит фокус к началу новой формы. Уже сохранённые ответы остаются в PostgreSQL. «Отменить добавление» доступно только при наличии сохранённых гостей и блокируется при активной отправке. Оно очищает текущий черновик и возвращает к подтверждению, не вызывая DELETE. После отмены можно сразу скачать PDF или снова добавить гостя.

Сохранение не считается успешным до успешного ответа POST. При ошибках форма остаётся доступной. CSRF, server-side validation, submission key, HttpOnly cookie и существующая notification outbox сохранены.

## 2. Максимум пять гостей

Общая константа `MAX_SESSION_GUESTS=5`. Считаются существующие записи session независимо от attendance. Проверка находится в `saveRsvp` после блокировки строки `guest_sessions FOR UPDATE`, внутри существующей транзакции. Проверка повторного submission key идёт до capacity check: повтор доставки пятого ответа остаётся idempotent. Шестой новый ответ получает 409.

UI скрывает добавление при пяти ответах и показывает понятный текст. Удаление организатором освобождает место, потому что счётчик основан на живых строках, а не cookie counter. Очистка/повреждение cookie обрабатывается существующим безопасным механизмом. IP/fingerprint не используются для определения числа гостей. Старые уже существующие данные не обрезаются и не удаляются. Миграция не нужна: текущая модель session-to-many-RSVP уже подходит.

## 3. Настоящий PDF

`src/server/pdf/ticket.mjs`: Node-only PDFKit, векторный текст и графика, встраиваемые локальные кириллические шрифты, локальная акварель и QR. Это не HTML screenshot, не внешняя PDF-служба и не отдельная база.

Оформление: A4 portrait, cream/olive/gold, акварельные листья, тонкие линии и swatches. По последней правке пользователя декоративные имена используют Cormorant Garamond regular, `&` использует Royal Kaynin, как Hero. Подпись «С любовью» отсутствует. На первой странице нет маленького верхнего дублирования имён/даты. На следующих имена слева, дата справа. Остаётся нумерация страниц. Hero, фотографии, opening и существующий motion не переделывались.

Один документ включает всех сохранённых гостей. На первой части имена, у declined гостя статус дополнительно указан сразу. Далее индивидуальные ответы. Для GOING: алкоголь, безалкогольное, горячая закуска, основное блюдо, оба трансфера, поздравление/совместное поздравление, ограничения питания при наличии. Organizer-only «Кто вы?» и музыка не перегружают памятку. Для NOT_GOING только имя и статус. Форматирование persisted полей переиспользует текущий `rsvpDetail`, не копирует ответы первого гостя.

После ответов: сообщение об изменениях с настоящими Telegram link annotations Ани и Максима. Далее дата, площадка, адрес, карта площадки, программа, обе палитры, ссылка на полный дресс-код, сайт и контакты. Полные guest blocks удерживаются вместе, измеряется высота строк. Для длинных данных число страниц естественно увеличивается.

## 4. Доступ и приватность

`GET /api/rsvp/invitation` использует только существующую opaque HttpOnly cookie. Произвольный RSVP ID не принимается как доказательство доступа. Загружаются только строки `WHERE session_id=$1`. Нет cookie/expired cookie: 401; нет ответов: 404; превышение лимита скачиваний: 429; ошибка генерации: 503 с безопасным сообщением.

Ответ: `application/pdf`, attachment filename `anya-maxim-invitation.pdf`, `Cache-Control: private, no-store`, `Vary: Cookie`, `nosniff`. Личные ответы не логируются. PDF не хранится в public и не кэшируется общим CDN. Лимит скачиваний 30 в час на session. Cookie не содержит имён. Local QA proxy вызывает тот же download handler и renderer с изолированной PGlite.

## 5. Публичные данные, QR и календарь

`src/content/wedding.mjs` стал общим источником даты, времени, программы, площадки, адреса, Telegram-контактов и публичного origin. До этого купленный домен не был выделен в текущей конфигурации. По явному указанию пользователя установлен `PUBLIC_ORIGIN=https://anyaxmaxim.ru`. Он не подменяет runtime `PUBLIC_SITE_URL` для локального API / Telegram. Изменение официального домена делается в одном месте.

QR ведёт только на публичный origin без персональных данных, ID или токенов. Генерация локальная, error correction M, четыре модуля quiet zone, 480px source, около 39 мм в PDF. Автоматический decoder подтвердил ссылку во всех трёх документах. Физическая печать/сканирование настоящим телефоном пока не выполнялись.

Существующий календарный сценарий сохранён. ICS теперь содержит название свадьбы, LOCATION, полный адрес, карту, сайт, пять времён программы, DTSTART 17.07.2027 12:00Z (15:00 Москва), DTEND 19:00Z (22:00 Москва), `X-WR-TIMEZONE:Europe/Moscow` и прежний VALARM за 7 дней. UTC timestamps однозначны и не сдвигают сам момент события между устройствами; календарь в другой зоне закономерно показывает локальное время. UTF-8 folding до 75 bytes сохранён. Отдельного Google Calendar сценария в проекте нет, новый параллельный сценарий не создавался. RSVP-ответы в календарь не попадают.

Для карты используется существующая ссылка поиска именно по названию площадки и полному адресу, общая с Venue. Это не ссылка на населённый пункт из FAQ про оставленную машину. Точный entrance pin не выдумывался.

## 10. Что осталось вне локальной проверки

Настоящий Safari/iOS, Android PDF viewers, macOS Preview, Acrobat и физическая печать не заменяются Windows WebKit и автоматическими PDF readers. Нужен отдельный ручной просмотр на этих устройствах. Не проверялись production storage/migrations (изменения schema не требуются), реальный внешний Telegram preview cache, production notification delivery и доступность купленного домена. Существующие Telegram auth/outbox tests проходят локально, тестовые отправки в живой бот не делались.

Отдельная находка `npm audit`: в существующем Next 16.3.8 сообщаются critical advisories, в транзитивном zod high; всего 18 advisories. PDFKit/qrcode не обозначены как источник этих high/critical. Автоматический `audit fix --force` и обновление framework не запускались, чтобы не расширять задачу и не менять startup flow. До будущего deployment следует отдельно обновить/проверить framework и повторить regression. Production этим проходом не изменён.
