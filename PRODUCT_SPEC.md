# Техническое задание --- интерактивное свадебное приглашение

## 1. Продукт

Создать интерактивный сайт-приглашение на свадьбу Ани и Максима.

Дата свадьбы: 17.07.2027\
Начало: 16:00\
Ориентировочно гостей: 25--30 человек.\
На первом этапе в гостевом разделе --- 22 человека: 11 родственников и
11 друзей.

Это не обычный свадебный лендинг. Сайт должен ощущаться как единое
цифровое приглашение с эмоциональным сценарием, сильной типографикой,
фотографиями, кинематографичным скроллом и аккуратными интерактивными
деталями.

Пользователь не предоставляет Figma-макеты. AI-агент самостоятельно
разрабатывает визуальную концепцию и реализует её в коде. Владелец
проекта выступает арт-директором: смотрит результат в браузере и даёт
текстовые правки.

## 2. Основные принципы

-   Design-first, но дизайн создаётся непосредственно в коде.
-   Не использовать готовый свадебный шаблон.
-   Не копировать Behance/шаблонные wedding websites.
-   Визуальный язык должен быть премиальным, современным и
    эмоциональным.
-   Анимация должна поддерживать историю, а не быть декоративным шумом.
-   Desktop и mobile проектируются одновременно.
-   Сайт должен быстро загружаться и работать на мобильных устройствах.
-   Все тексты, даты, адреса, изображения и данные гостей должны быть
    легко заменяемыми.
-   Архитектура должна позволять менять отдельные визуальные решения без
    переписывания backend-логики.

## 3. Технологии

Предпочтительный стек:

-   Next.js
-   TypeScript
-   React
-   PostgreSQL
-   Tailwind CSS или аккуратная собственная CSS-архитектура
-   серверные API/routes внутри Next.js либо эквивалентный безопасный
    backend
-   GitHub как репозиторий
-   Amvera как production hosting
-   PostgreSQL на российской инфраструктуре

Не использовать Vercel как production hosting.

Не использовать Yandex Forms или сторонний внешний сервис для RSVP.

## 4. Открывающая сцена

До основного сайта показывается интерактивный пролог.

Сценарий:

1.  Появляется конверт.
2.  На нём/рядом появляется красивая типографика, например: «На твой
    телефон пришло новое сообщение».
3.  Конверт открывается.
4.  Появляется письмо: «Вам пришло приглашение на свадьбу Ани и
    Максима».
5.  Кнопка: «Что за свадьба?»
6.  После нажатия письмо складывается в бумажный самолётик.
7.  Самолётик улетает.
8.  Следует эффектный переход/взрыв бумаги или другой подходящий
    transition.
9.  Открывается основной сайт.

AI-агент сам выбирает конкретную механику, easing, timing, typography и
visual treatment.

Пролог должен быть эффектным, но не раздражающим. Предусмотреть
корректную работу на мобильном и возможность не заставлять пользователя
повторно проходить длинную анимацию при каждом посещении.

## 5. Hero

Главный первый экран.

Крупная каллиграфическая надпись:

# Аня & Максим

Надпись должна быть одним из главных визуальных элементов проекта.

После/за типографикой появляется большая фотография пары.

Фотография намеренно может выходить за границы первого viewport и
продолжаться ниже экрана. Скролл должен ощущаться как продолжение
раскрытия фотографии.

Не делать обычный hero с маленьким фото и текстом по центру.

## 6. Дата и время

После hero:

# 17.07.2027

Ниже:

«Начало в 16:00»

Дата должна быть самостоятельным крупным визуальным объектом.

## 7. Место

Следующий основной блок.

Содержимое:

-   большая фотография места;
-   название места;
-   адрес;
-   информация о парковке;
-   информация о спальных местах;
-   большая кнопка перехода в Яндекс Карты.

Кнопка должна открывать конкретную точку/маршрут в Яндекс Картах.

Точный адрес и ссылка будут добавлены позже через конфигурацию проекта.

## 8. Dress code

Раздел:

# Дресс-код

Переключатель:

-   Для девушек
-   Для мужчин

Каждое состояние показывает визуальные примеры одежды.

Основные свадебные цвета/настроение:

-   белый;
-   оливковый;
-   золотой.

Не превращать раздел в длинную инструкцию. Основную информацию должны
передавать изображения и короткие подписи.

## 9. Кто будет

Раздел:

# Кто будет

Две категории:

-   Родственники --- 11 человек
-   Друзья --- 11 человек

Карточка гостя:

-   placeholder-фото на первом этапе;
-   имя;
-   короткое описание «кто это».

Пока использовать временные изображения. Реальные фотографии будут
добавлены позже.

Пример тона:

«Маша --- подруга невесты. Та самая, которая знает про Аню вообще всё».

Тон может быть тёплым и немного ироничным.

## 10. Примерная программа

Раздел:

# Как всё будет

Пока использовать примерный timeline:

16:00 --- встречаемся\
16:30 --- церемония\
17:00 --- фотографии и поздравления\
18:00 --- ужин\
20:00 --- танцы\
...

Финальное расписание будет изменено позже.

Визуально не делать банальный корпоративный timeline. Можно использовать
крупные часы, цифры и scroll-based transitions.

## 11. RSVP

Раздел:

# Ты придёшь?

Форма должна быть собственной, не внешним сервисом.

### Первый шаг

Поле:

«Ваше имя»

Переключатель:

-   Приду
-   Не приду

До выбора варианта остальные поля disabled.

### Если выбран «Не приду»

Показываются/активируются только необходимые поля:

-   имя;
-   выбранный статус.

После этого кнопка отправки становится активной.

### Если выбран «Приду»

Активируются:

1.  «Ваше имя»
2.  «Кто вы?»

Placeholder:

«Сват, брат, гений, миллиардер, плейбой»

3.  «Аллергии / особенности питания»

4.  Трансфер:

-   «У меня нет прав и друзей с машиной»
-   «Я уже смешарик (доеду сам/а)»

5.  Ночёвка:

-   «Да, я взрослый»
-   «Мне надо домой»

6.  Checkbox:

«Я приду по указанному дресс-коду»

Рядом/внутри --- ссылка или anchor-переход к разделу dress code.

Обязательными для «Приду» являются имя, статус, dress-code confirmation
и остальные поля, которые будут определены UX-решением агента. Не делать
форму чрезмерно бюрократичной.

Submit:

«Подтвердить участие»

Кнопка должна быть disabled, пока обязательные поля не заполнены.

## 12. После отправки RSVP

После успешной отправки форма заменяется confirmation state.

Текст:

«Вы успешно заполнили приглашение»

«Ждём вас 17.07.2027»

«Начало в 16:00»

Название места

Адрес

Кнопка:

«Скачать мой билет»

Гость не редактирует RSVP после отправки.

Если данные нужно изменить, администратор удаляет запись, после чего
гость может заполнить форму заново.

## 13. PDF-билет

Для каждого подтверждённого гостя генерировать персональный PDF.

В PDF:

-   Аня & Максим;
-   17.07.2027;
-   16:00;
-   место;
-   адрес;
-   имя гостя;
-   ответ на «Кто вы?»;
-   короткая информация о dress code.

Не включать рассадку.

PDF не должен выглядеть как технический чек. Это часть визуального опыта
приглашения.

AI-агент самостоятельно проектирует визуальный стиль PDF в соответствии
с сайтом.

PDF генерировать по запросу на сервере. Не обязательно хранить готовый
файл постоянно.

## 14. Guest session

Не создавать аккаунты для гостей.

После взаимодействия/отправки использовать secure HttpOnly cookie с
непрозрачным случайным идентификатором гостевой сессии.

Не хранить в cookie имя гостя.

Гость не получает полноценный личный кабинет.

Допускается, что очистка cookie позволит создать новый RSVP. Это не
считается критической проблемой: дубли при необходимости очищаются
администратором.

## 15. Admin

Отдельная защищённая админ-панель.

Администратор может:

-   авторизоваться по логину/паролю;
-   видеть список RSVP;
-   видеть количество пришедших/не пришедших/не ответивших;
-   видеть ответы гостей;
-   видеть аллергии/питание;
-   видеть необходимость трансфера;
-   видеть необходимость ночёвки;
-   видеть подтверждение dress code;
-   удалять RSVP;
-   после удаления освобождать связанные данные;
-   просматривать гостевой список.

Рассадка и места полностью отсутствуют в проекте.

Не строить полноценную CMS. Контент сайта на первом этапе редактируется
через код/конфигурацию.

## 16. Безопасность RSVP

Проверка обязательных полей должна происходить и на клиенте, и на
сервере.

Нельзя доверять только React state.

Сервер должен валидировать:

-   имя;
-   attendance;
-   поля для пришедших гостей;
-   длины строк;
-   допустимые значения enum;
-   cookie/session.

Предусмотреть базовую защиту от спама/ботов и rate limiting, если это не
усложняет deployment чрезмерно.

Админские credentials никогда не хранить в frontend.

Пароль хранить только в безопасном хешированном виде или через
безопасный auth-механизм.

## 17. Database

Минимально необходимы сущности:

### RSVP / guests

-   id
-   name
-   attendance
-   who_are_you
-   allergies
-   transfer
-   overnight
-   dress_code_confirmed
-   session_id/reference
-   created_at
-   updated_at

Гостевой публичный список можно хранить отдельно от RSVP, если это
удобнее для архитектуры.

### Guest profiles

-   id
-   name
-   category: family/friends
-   description
-   photo
-   sort_order

На первом этапе 22 записи.

## 18. Admin test mode

До публикации нужно иметь возможность:

-   заполнить форму тестовыми данными;
-   проверить оба состояния RSVP;
-   проверить PDF;
-   проверить admin;
-   удалить тестовые записи.

Никаких тестовых данных не должно остаться в production.

Предусмотреть безопасное удаление с подтверждением.

## 19. Responsive

Обязательные размеры:

-   desktop;
-   tablet;
-   mobile.

Mobile-first подход допустим.

Особое внимание:

-   огромной каллиграфической типографике;
-   большой фотографии hero;
-   opening animation;
-   карточкам гостей;
-   dress-code переключателю;
-   RSVP;
-   PDF.

Не просто уменьшать desktop layout.

## 20. Motion

Использовать анимацию осмысленно:

-   opening sequence;
-   появление/раскрытие hero;
-   движение фотографии;
-   scroll transitions;
-   появление даты;
-   интерактивность карточек;
-   переключение dress code;
-   раскрытие RSVP;
-   success state.

Не использовать десятки независимых эффектов одновременно.

Предпочтение --- несколько сильных, хорошо связанных transition.

Уважать prefers-reduced-motion.

## 21. Архитектура контента

Все легко меняемые данные вынести из компонентов:

-   дата;
-   время;
-   имя пары;
-   адрес;
-   карта;
-   парковка;
-   ночёвка;
-   программа;
-   гости;
-   dress-code;
-   изображения.

Не размазывать эти данные по JSX.

## 22. Что НЕ делать

-   Не делать рассадку.
-   Не делать guest accounts.
-   Не делать сложную CMS.
-   Не использовать Yandex Forms.
-   Не использовать Vercel production deployment.
-   Не требовать Figma.
-   Не превращать сайт в типовой wedding template.
-   Не перегружать анимациями.
-   Не добавлять функциональность только ради функциональности.

## 23. Definition of Done

Проект считается готовым, когда:

-   сайт запускается локально одной понятной командой;
-   production deployment описан и воспроизводим;
-   opening animation работает;
-   hero и scroll experience завершены;
-   все основные разделы работают;
-   RSVP работает на desktop/mobile;
-   сервер валидирует RSVP;
-   cookie/session работает;
-   admin защищён;
-   admin видит и удаляет RSVP;
-   PDF генерируется персонально;
-   PDF визуально соответствует сайту;
-   нет рассадки;
-   нет тестовых данных;
-   основные ошибки обработаны;
-   мобильная версия проверена;
-   accessibility basics соблюдены;
-   production build проходит без ошибок;
-   README содержит инструкцию запуска и деплоя.
